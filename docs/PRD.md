## 0. How to use this document

This PRD describes the **complete product**: what a finished, professional SoundCloud-style music platform does, screen by screen and rule by rule. It is written so that an implementer can build it without coming back with questions.

- **Normative words.** **MUST** = required for the product to be considered complete. **SHOULD** = expected; skip only with a written reason in `docs/REFACTOR.md`. **MAY** = optional polish.
- **Priorities.** Every feature has a priority: **P0** (core, build first), **P1** (needed for a complete product), **P2** (completes the experience; build last).
- **IDs.** Requirements have IDs (`UP-12`, `TR-4`, …) so tests, commits and the REFACTOR log can reference them.
- **Milestones.** §19 orders the work into milestones M0–M8. Each milestone ends green (types, lint, unit, integration, e2e).
- **Freedom to change the data layer.** This is not a production app. The implementer **MAY rename, modify or delete any table or field, drop the entire database, squash all migrations into a new baseline, and erase the R2 bucket (user uploads)**. The schema in §16 is a target design, not a constraint to preserve existing rows. The only things to keep from R2 are the demo source files used by the seed (`random-artwork-images/*` and the demo audio), and only if the seed still needs them.
- **This PRD supersedes** the domain glossary in `CONTEXT.md` where they disagree (notably: Release and Playlist become one **Collection** concept, and `UNLISTED` is replaced by private + secret link). Update `CONTEXT.md`, the ADR folder and the README as part of M0.
- **Keep what is good.** The engineering decisions in README "Decisions worth knowing" remain in force unless this document says otherwise: no audio proxying, browser-side waveform analysis, the `MediaAsset` lifecycle, counters that change only with real row changes, advisory locks for serialised writes, HMAC-keyed anonymous play dedupe, WebP artwork renditions.

### 0.1 Decisions taken with the product owner

| Topic | Decision |
|---|---|
| Collections | **One Collection model** with a type: `PLAYLIST`, `ALBUM`, `EP`, `SINGLE`, `COMPILATION`, exactly like the SoundCloud creator workflow. A multi-file upload creates an `ALBUM` by default; the type can be changed at any time. |
| Plans | **Simulated tiers, no billing.** Accounts are `FREE` or `PRO`. Pro is switched on in Settings with a "demo upgrade" (no payment). Features are gated through one entitlements module. |

| Moderation | **Basic trust & safety.** Report content/users, block users, admin page to review reports, remove content, suspend users, grant verified badges. Rate limits on abuse-prone actions. |

## 1. Product overview

### 1.1 Vision

A place where independent creators upload music and audio, publish it as tracks, albums, EPs, singles and playlists, and build an audience; and where listeners discover, play, save, share and talk about that music — **at the exact second they are hearing it**.

### 1.2 Goals

1. **Creators** can upload one track or a whole release in a single, clear flow, control visibility and permissions at both track and collection level, and see who is listening.
2. **Listeners** can find music (search, discover, charts, follows), play it continuously in a persistent player, and keep it (likes, playlists, library, history).
3. **Social loop**: follows, reposts, likes, timed comments and notifications make activity visible and bring people back.
4. **Professional quality**: fast, accessible, responsive (phone to desktop), secure, consistent counters, no dead buttons, no fake data in production paths.
5. **Runs on free tiers**: Vercel Hobby, Neon free, Cloudflare R2, Resend free.

### 1.3 Non-goals

- Real payments, payouts, royalties, distribution to other stores.
- Server-side transcoding (FFmpeg, HLS). Files are streamed as uploaded (see §3.3).
- Native mobile apps and true offline listening (DRM). The web app is responsive and installable (PWA manifest) but does not download audio for offline use.
- Live audio, stations generated by ML, ads.
- Multiple languages (UI is English; dates and numbers use `Intl` with the browser locale).

### 1.4 Success criteria (definition of "complete")

- Every workflow in §7 of the research doc ("Where the user goes after uploading") and every journey in §5 of this PRD works end to end in production.
- No visible control is non-functional. Anything not built is not rendered.
- Every P0 and P1 requirement has at least one automated test (integration or e2e) referencing its ID.
- Lighthouse (mobile, production build) on the track page: Performance ≥ 85, Accessibility ≥ 95, Best Practices ≥ 95, SEO ≥ 95.

## 2. Users, roles and plans

### 2.1 Personas

| Persona | Needs |
|---|---|
| **Listener** (signed out) | Play public music instantly, search, browse, share links. Prompted to sign in only when an action needs an account. |
| **Listener** (signed in) | Like, repost, comment, follow, build playlists, library, history, feed, notifications. |
| **Creator** | Everything a listener can do, plus upload, publish releases, edit metadata, manage permissions, Spotlight, insights. Every account is both a listener and a creator; there is no separate account type. |
| **Pro creator** | Simulated paid tier: unlimited upload time, scheduled releases, Quiet Mode, 5 Spotlight items, replace audio, full insights. |
| **Admin** | Review reports, remove content, suspend users, grant verified badges. |

### 2.2 Roles

`User.role`: `USER` | `ADMIN`. Admins are users whose email is listed in `ADMIN_EMAILS` (comma-separated env var) — the role is synced at sign-in — or who are promoted by the seed. Admin pages are under `/admin` and return 404 to non-admins.

### 2.3 Plans and entitlements (simulated)

All limits live in **one module** (`src/server/modules/plans/entitlements.ts`) exporting `getEntitlements(user)`. No other code compares `user.plan` directly. Limits are constants in a config object so they can be tuned in one place.

| Entitlement | FREE | PRO |
|---|---|---|
| Total upload time (sum of durations of the user's existing tracks) | 180 minutes | Unlimited (fair-use cap 50 GB stored audio) |
| Max file size | 100 MB | 100 MB (browser-side analysis decodes the whole file; see §3.3) |
| Spotlight items on profile | 1 | 5 |
| Scheduled release (publish at a future time) | — | ✓ |
| Quiet Mode (hide public stats on a track) | — | ✓ |
| Replace audio file of a published track (keeps comments, likes, plays, URL) | — | ✓ |
| Insights time ranges | Last 7 days + all-time totals | 7 d / 30 d / 90 d / 12 mo / all time |
| Insights breakdowns (countries, sources, top listeners, per-track drill-down) | — | ✓ |
| "PRO" badge on profile | — | ✓ |
| Custom audio preview clip, downloads, comments controls, embeds, license, all metadata | ✓ | ✓ |

**Plan switching** (`/settings/plan`, P1):

- PL-1 The page shows a two-column comparison of the table above and the current plan. Button: **"Upgrade to Pro (demo — no payment)"** / **"Switch back to Free"**. A notice states clearly that no payment is taken.
- PL-2 Switching is immediate and recorded (`planChangedAt`) and creates a `SYSTEM` notification.
- PL-3 **Downgrade never deletes or hides content.** Effects: uploads are blocked while the user is over the Free upload-time limit (the upload page explains why and how much to free up); Spotlight keeps the first item by position and hides the rest (restored on re-upgrade); scheduled tracks stay scheduled and publish normally; Quiet Mode stays on for tracks that already have it, but cannot be turned on for new ones; Insights shows Free ranges.
- PL-4 Every gated control is visible to Free users with a small "PRO" tag; activating it opens an upsell dialog linking to `/settings/plan` instead of failing silently. The server enforces every entitlement regardless of the UI (`FORBIDDEN` with code `PLAN_REQUIRED`).

## 3. Platform constraints

### 3.1 Infrastructure (unchanged)

One Next.js app (App Router) on **Vercel Hobby**, **Neon Postgres** (pooled URL at runtime, direct URL for migrations), **Cloudflare R2** for all binary objects, **Better Auth** for sessions, **tRPC** for app APIs, route handlers for media and webhooks. Stack versions per `package.json`.

### 3.2 Consequences that shape requirements

| Constraint | Consequence |
|---|---|
| Serverless functions, no long-lived processes or sockets | No WebSockets. "Live" things (notification badge, messages) use polling with `refetchOnWindowFocus` (see NT-6, MS-5). |
| Vercel Hobby cron runs at most once per day | Time-based behaviour MUST NOT depend on a cron firing on time. **Scheduled releases are evaluated at read time** (`publishAt <= now()`), not flipped by a job. The daily cron only does housekeeping (§15.3). |
| Short-lived requests | Post-response work (sending email, creating notifications, deleting R2 objects) uses Next's `after()`, backed by durable tables so a lost `after()` is recovered by the daily cron. |
| Free bandwidth budget | Audio and images are never proxied through functions. Clients get `307` redirects to presigned (or public) R2 URLs. |
| No transcoding | Audio is played in its uploaded format. Waveform + duration are computed in the uploader's browser (existing design). |
| Neon free compute | Read paths must be index-backed; heavy aggregates (insights, charts) read pre-aggregated daily tables (§16). |

### 3.3 Audio formats and processing

- UP-F1 Accepted: MP3, M4A/AAC, WAV, FLAC, OGG (Vorbis/Opus), AIFF. Validated by extension **and** sniffed magic bytes on the server after upload (the current HEAD check plus a ranged GET of the first 64 bytes).
- UP-F2 The uploader's browser MUST be able to decode the file (Web Audio `decodeAudioData`). If decoding fails, the file is rejected with "Your browser can't read this file. Try MP3, WAV or FLAC." There is no "no waveform" state for new uploads anymore.
- UP-F3 Tracks store `mimeType`. The player checks `audio.canPlayType(mimeType)` before playback; when it returns `""` the track row shows "Can't play this format in your browser" and the queue skips it.
- UP-F4 Max duration per file: 4 hours (sanity limit; also bounded by upload time and file size).

### 4.2 Permalink rules

- IA-1 **Username**: 3–25 chars, `[a-z0-9_-]`, starts with a letter or digit, unique (case-insensitive; stored lowercase). Reserved words cannot be usernames: every first-level route segment above plus `api, embed, admin, static, _next, me, you, settings, help, about, login, logout, new, sets, tags, charts, stations, pages, assets, null, undefined` (keep the list in one module and test it against `src/app` directory names).
- IA-2 **Track slug**: generated from the title (`slugify`, lowercase, ascii, max 80), unique per creator; collisions get `-2`, `-3`. Reserved track slugs (collide with profile sub-routes): `popular-tracks, tracks, albums, sets, reposts, likes, followers, following, comments, spotlight`.
- IA-3 **Collection slug**: same rules, unique per owner, under `/sets/`.
- IA-4 Creators MAY edit the slug (the "Permalink" field). Old usernames and old slugs are stored in redirect tables; requests to an old URL `308` to the current one. A freed old username becomes available to others after 30 days; until then it redirects.
- IA-5 **Secret links**: each private track/collection has a random 22-char URL-safe `secretToken`. "Reset secret link" generates a new token and invalidates the old one immediately.
- IA-6 Time links: `#t=1m23s` (or `#t=83`) on a track URL seeks there when the user presses play (SoundCloud-compatible).

## 6. Accounts, authentication and onboarding

### 6.1 Sign up / sign in (P0)

- AU-1 Methods: email + password, Google OAuth (existing). Better Auth stays the auth library (use its email-verification, password-reset and, if convenient, username plugins).
- AU-2 `/signin` and `/signup` are full pages **and** reachable as a modal from any "Sign in to …" prompt; after success the user returns to where they were and the pending action is retried once (e.g. the like they clicked).
- AU-3 Password: min 8 chars, rejected if in a small common-password list (top 1 000). Show/hide toggle. Rate limited (Better Auth limiter stays on).
- AU-4 Email verification: on email sign-up a verification email is sent (Resend). Unverified users can listen, like, follow and build playlists, but **upload, comment, repost and message require a verified email**; those actions show "Verify your email to …" with a "Resend email" button (max 3 per hour). Google accounts are verified automatically.
- AU-5 Password reset: `/forgot-password` (always answers "If an account exists, we sent a link" — no account enumeration) → email link valid 1 hour, single use → `/reset-password` → all other sessions revoked.
- AU-6 Sessions: "Sign out everywhere" in Settings → Account lists active sessions (device/browser from UA, last active, approximate location from `x-vercel-ip-country`) with per-session revoke.

### 6.2 Onboarding (P0)

`/onboarding` is forced (redirect from any page except auth/legal/onboarding) until `onboardedAt` is set.

1. **Profile basics** — Username (live availability check, suggestions on conflict), Display name (1–50 chars; defaults to Google name or email local part), Avatar (optional; Google image pre-filled, processed through the image pipeline §8.10).
2. **Genres** — pick at least 3 of the genre list (stored in `User.favoriteGenres`; seeds recommendations).
3. **Follow creators** — 12 suggested creators (most-followed creators with public tracks in the chosen genres, excluding self), each with avatar, name, follower count, a play button for their top track and a Follow toggle. "Skip" allowed.
4. Done → redirect to `/` (Home).

### 6.3 Account settings (P1) — `/settings`

- AU-7 Change email (requires password or a fresh Google sign-in; verification email to the new address; old address gets a notice).
- AU-8 Change password; set a password on a Google-only account.
- AU-9 Connected accounts: link/unlink Google (cannot unlink the last sign-in method).
- AU-10 **Delete account**: type username to confirm. Effects in one transaction: status `DELETED`, sessions revoked, content hidden immediately; then (in `after()`, completed by cron) hard-delete the user's rows, **recount every denormalised counter the deletion affects** (likes, reposts, comments, follows, collection track counts — see §16.4), enqueue all their R2 objects in `StorageDeletion`, free the username after 30 days. Their comments on others' tracks are deleted; their tracks are removed from other users' playlists (playlists show "A track was removed" no longer).

## 7. Upload and publishing

This section implements research doc §3, §7.2 and §10.1–10.7.

### 7.1 Upload page structure (P0)

`/upload` has two stages on one page, without a full page reload between them:

**Stage A — Choose files**

- UP-1 Large drop zone: "Drag and drop your tracks & albums here" + **Choose files** button (multi-select). A checkbox **"Make a playlist when multiple files are selected"** is checked by default (SoundCloud behaviour: multiple files → collection). Shows the account's upload-time usage bar ("47 of 180 minutes used" or "Unlimited — Pro") and accepted formats/size.
- UP-2 Files are validated client-side immediately (type, size, count ≤ 100 per batch, remaining upload time once durations are known). Invalid files are listed with the reason and excluded; valid files continue.
- UP-3 Selecting **1 file** → single-track editor. Selecting **2+ files** with the checkbox on → release editor; with it off → N independent single-track editors stacked (each saved separately, "Save all" button).

**Stage B — Editor** (shown immediately while files upload in the background)

### 7.2 Per-file pipeline and states (P0)

Each file runs: `Queued → Uploading (bytes %) → Analysing (decode, duration, peaks) → Verifying (server checks type, size, quota; stores waveform) → Ready` or `Failed`.

- UP-4 Concurrency: 3 parallel uploads; the rest are Queued. Analysis runs in parallel with upload (existing design) but at most 2 decodes at a time (memory).
- UP-5 Each track row shows its state, a progress bar, and on failure the reason + **Retry** + **Remove**. A failed file never blocks other files; the batch can be saved once every remaining file is Ready (failed ones must be retried or removed).
- UP-6 An overall batch progress bar sits above the track list ("3 of 5 ready").
- UP-7 `beforeunload` warns while anything is uploading or unsaved. Leaving cancels pending assets (best-effort `cancelUpload`; the daily cron expires the rest).
- UP-8 Upload time quota is enforced on the server at **Verifying** using the analysed duration (reject with `UPLOAD_LIMIT_REACHED`, delete the object) and again at save.
- UP-9 Title is pre-filled from the filename (strip extension, replace `_`/`-` with spaces, trim track-number prefixes like `01 - `). For MP3/FLAC/M4A, the client MAY read ID3/Vorbis tags (`music-metadata-browser` or a light parser) to pre-fill title, artist, album, track number, genre, year and embedded artwork — P2.

### 7.3 Single-track editor (P0)

Tabs: **Basic info · Metadata · Permissions · Advanced**. Fields and validation:

| Tab | Field | Rules |
|---|---|---|

| Basic | Permalink | `/{username}/` + slug, editable, live availability check. |

| Basic | Privacy * | **Public** / **Private** / **Schedule** (PRO; date-time picker in user's time zone, stored UTC, must be ≥ 5 min in the future, ≤ 1 year). |

- UP-10 Bottom bar: **Cancel** (confirm if dirty) · **Save** (disabled until Ready + valid). On save, track is created and the user is redirected to the **track page** with a success banner: "Your track is live" / "Your track is private — only people with the link can hear it" / "Scheduled for 12 Dec, 18:00", plus actions **Copy link**, **Edit**, **Upload another**, **Go to profile** (research §7.2 step 2).

### 7.4 Release editor — multi-file upload (P0)

Two clearly separated areas (research §10.1):

**Left / top: Release details**

| Field | Rules |
|---|---|
| Release artwork | As track artwork. Help text: "Release artwork doesn't replace each track's own artwork." Checkbox **"Use for tracks without artwork"** (default on). |
| Release title * | 1–100. Visually larger than track titles; labelled "Release title". |
| Permalink | `/{username}/sets/` + slug. |
| Type * | Segmented control with helper text (research §10.3): Playlist — "A collection or mix of tracks", **Album (default)** — "A full-length release", EP — "A shorter multi-track release", Single — "A standalone single release", Compilation — "Tracks grouped as a compilation". ### 7.7 Visibility model (P0)

`Visibility`: `PUBLIC` | `PRIVATE` | `SCHEDULED` (tracks only). Plus orthogonal `moderationState` (`VISIBLE` | `REMOVED`) and the owner's account `status`.

**Effective visibility** (one pure function `effectiveVisibility(entity, now)` used by every query and route): `SCHEDULED` with `publishAt <= now` ⇒ `PUBLIC`; `SCHEDULED` otherwise ⇒ `PRIVATE`; content whose owner is `SUSPENDED`/`DELETED` or whose `moderationState = REMOVED` ⇒ hidden from everyone but admins (the owner sees it with a "Removed" banner if removed by moderation; a suspended owner cannot sign in).

| Can the viewer… | Public | Private, plain URL | Private, valid secret link | Private track inside a collection opened via the collection's secret link |
|---|---|---|---|---|
| See the page / play | everyone | owner only (others: 404) | everyone | yes, if the track's owner = the collection's owner; otherwise no |
| Appear in profile, feeds, search, discover, charts, tags, sitemaps | yes | no | no | no |
| Like / repost / add to own playlist | signed in, not owner (VI-2) | owner may add to own playlists | no (button disabled with tooltip "Private tracks can't be liked or reposted") | no |
| Comment | signed in, verified, comments allowed | owner | signed in, verified | no (comment on the track page) |
| Download | if enabled, signed in | owner | if enabled, signed in | no |
| Embed | if allowed | no | if allowed (embed URL carries the token) | — |

- VI-1 Denied and missing both return **404** (never 403) to avoid leaking existence. The stream, waveform, artwork, download and play routes accept `?s=<token>` (track secret) or `?c=<collectionId>&s=<token>` (collection secret).
- VI-2 Users **cannot like or repost their own** tracks or collections (research §6.1, §6.5); the like button is hidden on own content, replaced by the counter.
- VI-3 In collections, tracks the viewer cannot play are shown as greyed rows "This track is not available" (no title, keeps numbering) and are skipped by playback. Owners see them normally with a "Private" pill.
- VI-4 Private collections never appear publicly; a private playlist added to a library by like is impossible (can't like private).

## 8. Listening

### 8.1 Player (P0)

Builds on the existing Zustand store (`src/store/player.tsx`), single `<audio>` element, Media Session.

- PL-P1 Controls: previous (restart if > 3 s in, else previous track), play/pause, next, **shuffle** (Fisher–Yates over the remaining queue; turning off restores original order), **repeat** (off → all → one), seek bar with hover time tooltip and buffered range, elapsed/total time, volume slider + mute (persisted), artwork/title/creator (links), like, follow creator (if not self), **Next up** toggle.
- PL-P2 **Queue model**: `context` (the list the user played from: a collection, a profile tab, likes, search results, a feed page…) + `userQueue` ("Play next" / "Add to Next up" items, played before the context continues) + `history` (last 50). Playing a track from a list sets the context to that list and starts at that track.
- PL-P3 **Next up panel** (desktop: right drawer; mobile: in the full-screen sheet): sections "Now playing", "Next up" (user-queued; drag to reorder, remove), "Next from: <context name>", "History" (collapsible); "Clear" button; each row has play, like, remove.
- PL-P4 Track row "…" menus everywhere include **Play next** and **Add to Next up**.
- PL-P5 **Autoplay**: when the queue ends, continue with related tracks (§10.6) if the "Autoplay" toggle (in Next up, default on) is on; label the section "Autoplay: based on <last track>".
- PL-P6 **Persistence**: queue, position (saved every 5 s and on `pagehide`), volume, shuffle/repeat/autoplay are stored in `localStorage` (try/catch). On reload the player restores paused at the saved position; it never autoplays on load.
- PL-P7 **Keyboard shortcuts** (ignored while typing in inputs): `Space` play/pause, `Shift+→/←` next/previous, `→/←` seek ±5 s (when focus is not on a slider), `↑/↓` volume (with Shift), `M` mute, `L` like current, `R` repost current, `S` shuffle, `Q` toggle Next up, `?` shortcuts dialog. Shortcut list in the user menu.
- PL-P8 Media Session: metadata with all artwork renditions, actions play/pause/previoustrack/nexttrack/seekto/seekbackward/seekforward; `setPositionState` kept current.
- PL-P9 **Play counting**: existing rules (one count per listener per track per 30 min, after 5 s of actual playback) + the play record carries `source` (§16) and the collection id when played from one. On track end/change/`pagehide`, a `navigator.sendBeacon` updates `listenedMs` and `completed` (≥ 90 % listened) for that play event. Plays by the track's owner are recorded for history but **not counted** in `playCount` or insights.
- PL-P10 Errors: network/decoding error → toast "Couldn't play <title>", skip to next after 2 s; presigned URL expiry (1 h) mid-session is handled by re-requesting the stream URL and resuming at the same position.
- PL-P11 Only one tab plays at a time (`BroadcastChannel`: when another tab starts playing, this one pauses).

### 16.3 Visibility in queries

All listing/search/feed queries MUST use shared Prisma `where` builders (`publicTrackWhere(now)`, `accessibleTrackWhere(viewer, now)`, same for collections) — no hand-written visibility conditions. Unit-test them and keep an integration test per surface asserting private, scheduled, removed and suspended content never appears.

### 16.4 Denormalised counters

Every counter changes **only by the number of rows actually inserted/deleted, in the same transaction** (existing `TrackLike` pattern), or is recomputed from rows. List and rule:

| Counter | Source rows | Serialisation |
|---|---|---|
| Track.likeCount / repostCount | TrackLike / TrackRepost | row ops + `GREATEST(0, …)` |
| Track.commentCount | Comment | advisory lock per track (existing) |
| Track.playCount / downloadCount | counted PlayEvent / dedupe window | advisory lock per (track, client) (existing) |
| Collection.likeCount / repostCount / playCount | CollectionLike / CollectionRepost / PlayEvent | row ops |
| Collection.trackCount / durationMs | CollectionTrack | advisory lock per collection |
| Comment.likeCount | CommentLike | row ops |
| User.followerCount / followingCount | Follow | row ops |
| User.publicTrackCount | Track | recomputed on publish/unpublish/delete |

Account deletion and blocking MUST recompute affected counters (a `recount*` helper per counter, also exposed as `pnpm db:recount` for repair). Integration tests assert counter = rows after every scenario.

## 18. Non-functional requirements

### 18.1 Background work (§3.2)

- BG-1 Daily cron (`vercel.json` `crons`, one entry): expire PENDING assets older than 24 h → `StorageDeletion`; drain `StorageDeletion` (up to the time budget); purge deleted accounts; send notification digests; prune `RateLimitBucket` (> 2 days), `EmailMessage.bodyHtml` (> 7 days), `PlayEvent` (> 13 months), expired username redirects; snapshot chart ranks (P2). Each task is idempotent and bounded (resume next day if the time budget is reached; log counts).
- BG-2 `after()` hooks: send immediate emails, create notifications that are expensive to compute, drain up to 20 `StorageDeletion` rows.

### 18.2 Performance

- NF-1 Server-render first paint for all public pages (RSC + tRPC prefetch + hydrate, as today). No client waterfall for above-the-fold data.
- NF-2 p95 tRPC latency < 300 ms for reads on seeded data (Neon free, warm). Every list query uses an index (check with `EXPLAIN` in an integration test for the feed, search, profile tabs and charts).
- NF-3 Images: renditions + `srcset/sizes` everywhere (existing). Avatars 64/160/320, banners 1240/2480, artwork 96/320/640.
- NF-4 JS budget: initial route JS ≤ 200 KB gzip for the track page; heavy widgets (charts, dnd, crop) loaded lazily.
- NF-5 Waveform JSON cached (immutable for public tracks; private: `private, max-age=3600`).

### 18.3 Security and privacy

- SC-1 Every mutation checks ownership/visibility in the service layer (not only in the router) and is covered by an integration test for the forbidden case.
- SC-2 All user text is rendered as text (React escaping); linkification produces anchors from a strict URL regex; no `dangerouslySetInnerHTML` for user content. Email templates escape all user content.
- SC-3 Security headers: CSP (self + R2 public/presigned hosts for media/img + Google for OAuth), `frame-ancestors` per SH-2, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` minimal.
- SC-4 Presigned GET TTL 1 h (stream), 5 min (download); PUT TTL 15 min. Secret tokens compared in constant time.
- SC-5 No raw IPs stored (HMAC as today); country code only. Privacy page documents data use.
- SC-6 Cron and unsubscribe endpoints verify secrets/signatures. Admin procedures check `role` server-side.
- SC-7 CSRF: Better Auth cookies `SameSite=Lax`; mutations only via POST tRPC.

### 18.4 Accessibility (WCAG 2.2 AA)

- A11Y-1 All controls keyboard reachable with visible focus; icon buttons have `aria-label`s that include state ("Like Blue Hour", `aria-pressed`).
- A11Y-2 Waveform is a `slider` (`aria-valuemin/max/now`, `aria-valuetext="1 minute 23 seconds of 3 minutes 15"`), arrow keys seek.
- A11Y-3 Drag-and-drop reorder has a keyboard alternative (UP-13) and announces moves via a live region.
- A11Y-4 Toasts and "now playing" changes are announced politely; dialogs trap focus and restore it.
- A11Y-5 `prefers-reduced-motion` disables marquee titles, equaliser animations and carousel auto-scroll.
- A11Y-6 axe checks in Playwright on the main pages (0 serious/critical).

### 18.5 SEO

- SEO-1 `sitemap.xml` (index + chunked sitemaps of public profiles, tracks, collections; `lastmod`), `robots.txt` disallowing `/studio`, `/settings`, `/you`, `/admin`, `/api`, `/embed`, secret links.
- SEO-2 Canonical URLs (permalinks), metadata per §8.3/§8.4/§9.1, `noindex` for private, removed, search results.

- OB-1 Structured server logs (JSON: route/procedure, userId, duration, error code); no secrets or tokens in logs.
- OB-2 Custom `not-found` and `error` pages in the app's style with a search box and links home; global error boundary keeps the player alive.
- OB-3 Vercel Web Analytics/Speed Insights MAY be enabled (free tier).

## 20. Seed and demo data

`pnpm db:seed` (idempotent; refuses to run against production unless `--force`) creates a believable world:

- 1 admin (`ADMIN_EMAILS`), 12 creators with avatars, banners, bios, links, varied genres; 2 Pro creators; 40 listener accounts.
- 60–80 public tracks (reusing the demo audio already in R2 and the artwork pool; several tracks may share an audio file), 3 private tracks (with secret links), 1 scheduled track (Pro creator, publishes in 2 days), 6 albums/EPs/singles, 8 playlists (some mixing creators), Spotlight items.
- Follows graph (power-law), likes, reposts, timed comments with replies and comment likes, play events spread over the last 120 days with sources and countries (so charts and insights are populated), daily stats derived from them, notifications for the demo login.
- A documented demo login (`demo@…` / password in `SEED_README.md`) that is onboarded and follows several creators.
- All seed passwords and emails are clearly fake; no real personal data.

## 22. Assumptions and open points

- **A1** Username is a new required field; existing accounts are reset anyway (fresh database), so no backfill is needed.
- **A2** "Unlisted" is expressed as Private + secret link (SoundCloud model). If a separate unlisted state is wanted later, add it to `Visibility` and the matrix in §7.7.
- **A3** Liking one's own content is not allowed (SoundCloud parity, VI-2) — this changes current behaviour where creators can like their own tracks.
- **A4** Collections can contain any accessible tracks regardless of type (SoundCloud parity); the type controls presentation (Albums vs Playlists tab), not membership.
- **A5** Plan limits in §2.3 are tunable constants; the free-tier R2 storage (10 GB) is the practical ceiling for the demo.
- **A6** Country analytics rely on the Vercel `x-vercel-ip-country` header; locally it is absent and stored as null ("Unknown").
